# AGENTS.md — FinanceApp

Operating rules for every AI agent working in this repository. These are
project contracts, not suggestions. When a situation is not covered here and
the consequence is real, stop and ask the maintainer instead of improvising.

## 1. Language

- **All code artifacts in English**: identifiers, function and struct names,
  comments, error messages, log messages, UI strings, test names, fixtures,
  commit messages.
- Product-facing prose (the README) follows the maintainer's decision —
  currently Spanish. Do not switch it unilaterally; extending it in Spanish
  is correct.
- `docs/` is developer documentation: extend it in its current language
  (Spanish) and keep a neutral, professional register.

## 2. Programming practices

- Follow the existing patterns of each stack before introducing new ones:
  Tauri/React in `apps/desktop`, Go in `backend/`, Python in `apps/processor`.
- Reuse existing helpers instead of re-implementing them: error mapping goes
  through `translateError` (`backend/internal/repositories/util.go`) and the
  repository-level taxonomy (`ErrNotFound`, `ErrConflict`, `ErrConstraint`,
  `ErrInternal`, `ErrUnavailable`).
- Every behavior change ships with its test. Observe RED before implementing
  when a deterministic test applies; never claim a fix without command
  evidence.
- Commits: Conventional Commits, in English, no `Co-Authored-By` and no AI
  attribution. Group into reviewable units: behavior, tests and docs
  together.
- `go build ./...`, `go vet ./...` and the relevant tests must pass before
  any commit. In this repo that means the whole suite, it takes seconds.
- The Go code under `backend/internal/db/` is **generated by sqlc**: never
  edit it by hand. Change migrations (`backend/internal/db/migrations/`)
  and query sources (`backend/db/queries/`), then regenerate. The full
  procedure and its rules (column order, trailing `;`, no `;` inside SQL
  comments) is documented in `docs/development.md`.
- Migrations are additive and idempotent; when changing a value catalog,
  translate existing rows instead of breaking them.
- Deleting code that "looks unused" requires evidence first: grep the whole
  repo, report the findings, and wait for the maintainer's decision.

## 3. Branching, pushing and delivery (hard rules)

- **Never push to `main`. Not once, not "just this small fix", not even if
  asked indirectly.** `main` moves only by the maintainer's explicit action
  (a pull request he merges).
- Work on `developer` or on feature branches created from it; push there.
- Do not open pull requests targeting `main`, do not merge into `main`, do
  not force-push any shared branch, and do not rewrite published history.
- Ask before: destructive git operations, any remote operation beyond
  pushing your feature branch, publishing, releases and tags, and deleting
  files the maintainer has not explicitly listed.
- An authorized change includes implementing, testing and documenting it.
  Never stop mid-task to ask permission for the next step of the same
  authorized work.

## 4. Architecture boundaries (verified facts)

- Components run by runtime: `apps/desktop` (Tauri shell + React/Vite
  frontend), `apps/processor` (Python document processing), `backend/`
  (Go, single module `financeapp/backend`).
- The desktop shell spawns the backend, waits for `GET /health` on port
  `8081`, and passes configuration via environment variables.
- All user data is local (`%APPDATA%\FinanceApp`): SQLite database,
  artifacts and logs. Nothing financial leaves the machine.
- CI runs `sqlc diff` on every push to `main`: a schema/query change without
  regeneration fails the pipeline.

## 5. Working style with the maintainer

- Verify before you assert. Never agree with a claim you have not checked
  against the code, and say so when the maintainer's assumption is wrong —
  with evidence.
- Report evidence, not vibes: commands and their actual output.
- Ask exactly one focused question when a genuine product or business
  decision is open; then wait.
- Do not fabricate RED/GREEN evidence, test results or approvals. If a
  check fails, say it failed and show why.
- Keep the maintainer in control: he decides delivery, branches, merges and
  anything user-visible.

## 6. Folder READMEs (standard)

Every main folder of the repository keeps a `README.md` with exactly three
sections, in this order:

1. **Resumen** — what lives in the folder and what it is for, in two to four
   lines.
2. **Estructura** — the folder rendered as a tree with working relative
   hyperlinks: one entry per file or directory, each with a one-line purpose
   note. Links resolve from the README's own location.
3. **Estado** — the current verified state: versions, what passes (with the
   command that proves it), what is pending or broken. Never list a check you
   did not run.

Rules:

- "Main folders" are the runtime and product folders (`apps/desktop`,
  `apps/processor`, `backend`, `docs`) plus any new top-level folder holding
  product code or shipped configuration.
- Folder READMEs follow the repository documentation language (Spanish);
  code artifacts stay English.
- A folder README is updated in the same commit that adds, moves or removes
  files in it: the tree is a map of the folder, not a changelog.
- The root `README.md` is the product page (badges, download, license) and
  keeps its own format; this standard applies to every other folder.
- Local user data (`data/`, `backend/data/`, `backend/logs/`, `backend/out/`)
  never enters the repository and gets no README.

### Per-component commands (hard rule)

- **Backend (Go)**: every command runs from `backend/`, the module root:
  `go build ./...`, `go vet ./...`, `gofmt -l .`, `golangci-lint run ./...`,
  `sqlc generate` (and `sqlc diff` to verify). The binary is started with
  `go run ./cmd/financeapp` from `backend/`, never from the repo root.
- **Desktop (`apps/desktop`)**: in local developer mode **the build is
  always `npm run build`**, which runs `tsc --noEmit` before bundling. A
  bare `vite build` silences type errors: that omission already produced
  one broken commit (ff875da, fixed in cd81ddd), and this rule exists so
  it never happens again.

### Mandatory verification battery

After any change to a component, run that component's battery from its
root and report the evidence (exit codes and counts). A change without
green evidence is not done. State of record on 2026-10-24: all three
batteries green.

- **Backend** (from `backend/`): `gofmt -l .` (empty = formatting OK),
  `goimports -l .` (empty = imports OK), `go build ./...`,
  `go vet ./...`, `go test -count=1 ./...`, `golangci-lint run ./...`
  (0 findings), and `sqlc diff` (must stay clean) whenever migrations or
  `backend/db/queries/` changed.
- **Processor** (always the env interpreter, never bare `python`):
  `<python.exe> -m compileall -q apps/processor` (everything compiles),
  `<python.exe> -m tabnanny -q apps/processor` (consistent indentation),
  `<python.exe> -m ruff check apps/processor` (lint, 0 findings — ruff is
  installed in the env since 2026-10-24), and the seven suites
  `<python.exe> tests/<file>.py`.
- **Desktop** (from `apps/desktop/`): `npm run build` (the type gate),
  `npm run lint` (0 problems), `npm test`, `npm run format:check`.

## 8. Version bumps and releases (hard rules)

A version bump touches a FIXED list of files. When the maintainer declares a
version ready ("todo listo", "release vX.Y.Z"), walk this list and verify each
one before reporting the bump done:

| File                                     | Field to change                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| `apps/desktop/package.json`              | `"version"` (the sidebar label reads it)                                                    |
| `apps/desktop/package-lock.json`         | the two ROOT entries (`""` and `packages[""]`) — never a dependency version                 |
| `apps/desktop/src-tauri/tauri.conf.json` | `"version"` (the MSI installer version)                                                     |
| `apps/desktop/src-tauri/Cargo.toml`      | `[package] version`                                                                         |
| `apps/desktop/src-tauri/Cargo.lock`      | the `financeapp-tauri` entry only                                                           |
| `apps/processor/src/main.py`             | `PROCESSOR_VERSION` (`CONTRACT_VERSION` is the artifacts contract, NOT the release version) |
| `backend/README.md`                      | "Versión del componente"                                                                    |
| `README.md` (root)                       | the version badge and the Releases list                                                     |
| `docs/README.md`                         | the public-version line                                                                     |
| `CHANGELOGS.md`                          | a new entry for the version                                                                 |

Rules:

- After the bump, `grep` the OLD version across the repo and report what you
  found: the only legitimate leftovers are dependency versions inside lockfiles,
  test fixtures that reproduce old payloads, and the history under
  `odd/tasks/`. Anything else is a miss.
- The `CHANGELOGS.md` entry (Spanish, like the repo prose) lands in the SAME
  commit as the bump: what was fixed, added and refactored per component, with
  the battery evidence.
- Run the desktop battery after the bump: `version.test` pins the component
  version to `package.json` and fails on drift.
- The tag and the GitHub release are maintainer actions. Never create a tag,
  never push to `main`, and never mark a version public before the release
  exists: docs say "complete on `developer`, pending publication" until then.
